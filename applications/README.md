# applications

The workloads' configuration — values files only. There are **no Application
manifests here**: every workload Application is generated by the ApplicationSet
in `environments/applicationset.yaml`, one per `environments/<env>/<app>.yaml`
(see `environments/README.md`). Nothing in this directory is applied as a
Kubernetes object; the files are read through each Application's `$values`
source ref.

```
applications/
  kovo/
    values.yaml         <- the app's configuration (prod-only app: all of it)
  new-tab-links-backend/
    values.yaml         <- shared by every environment
    prod.yaml           <- prod only
    dev.yaml            <- dev only
```

## Values layering

Each Application loads, in order — later files win:

1. `applications/<app>/values.yaml` — shared by every environment.
2. `applications/<app>/<env>.yaml` — this environment only; loaded when the
   environment file says `envValuesFile: true`.
3. `versions/<name>.yaml` (and `versions/<name>-init.yaml`) — image tags, CI's.

**An app that runs only in prod needs no split**: everything stays in
`values.yaml`, and there is no `prod.yaml`.

**An app in more than one environment keeps every environment-specific key
out of `values.yaml`**: `name`, `host`, `wwwAlias`, `replicas`, and any env var
that names a host, an origin, an issuer or a database. Each `<env>.yaml` sets
all of them. The reason is the failure mode: a key left in the shared file is
inherited by every environment whose own file forgets it, so a forgotten `host`
in `dev.yaml` would have the dev Ingress claim the prod host. Kept out, a
forgotten `name` fails the render (the chart requires it), and a forgotten
`host` falls back to the chart's default — no Ingress — rather than to prod's.

`name` must equal the Application name — `<app>` in prod, `<app>-<env>`
elsewhere. The chart derives the namespace, the Infisical folder, the Secret and
the Ingress from it.

Helm merges maps, so `env:` in `<env>.yaml` adds to and overrides the shared
`env:` key by key. Lists (`initContainers`, `persistence`) are replaced
wholesale — keep a list in one file.

For the NewTabLinks pair, the coupling is per environment: the backend's CORS
and websocket origins list the website's host *in the same environment*, and
the website's `NEWTABLINKS_BACKEND_BASE_URL` is the backend's public host in the
same environment. Changing a host means changing both `<env>.yaml` files.

## Chart version pinning

The chart lives in
[kovostack-helm-charts](https://github.com/Kovospace/kovostack-helm-charts) and
each app pins a tag **per environment**, in `environments/<env>/<app>.yaml`:

```yaml
chartRevision: chart-app-1.5.0
```

The ApplicationSet turns that into the Application's chart source, next to the
`$values` source that tracks `main`:

```yaml
sources:
  - repoURL: git@github.com:Kovospace/kovostack-helm-charts.git
    targetRevision: chart-app-1.5.0     # chart, pinned
    path: charts/app
    helm:
      valueFiles:
        - $values/applications/nsr/values.yaml
        - $values/versions/nsr.yaml
  - repoURL: git@github.com:Kovospace/kovostack-infra-gitops.git
    targetRevision: main                 # values, live
    ref: values
```

**Separate repositories is what makes this work.** ArgoCD rejects a multi-source
Application referencing two revisions of the *same* repo, so while the chart sat
in `charts/app` here it could not be pinned at all — the `$values` source has to
stay on `main` for CI deploys to take effect:

```
cannot reference a different revision of the same repository
```

Upgrading a chart is per app and per environment: bump one app's
`chartRevision` in `environments/dev/` (if it runs there), watch it, then in
`environments/prod/`, then move to the next app. Previously every app tracked
the chart at `main`, which is how a single bad annotation broke every workload
at once.

## Promotion

- **Chart change** — dev pin, then prod pin (`environments/<env>/<app>.yaml`).
- **Configuration change** — `applications/<app>/dev.yaml` first; once it
  works, move it to `prod.yaml` if it is environment-specific, or to the shared
  `values.yaml` (and out of `dev.yaml`) if every environment should have it.
- **Image** — the dev pipeline writes `versions/<app>-dev.yaml`; promoting a
  build is the same tag in `versions/<app>.yaml` (`versions/README.md`).

Every one of these is a push to `main`, and a push to `main` deploys — dev
included.

Releasing a new chart version is documented in the charts repo. Tag convention
is **`chart-<chart_name>-<semver>`**.

## Adding an app

Run `/new-app` in Claude Code and answer six questions — name, environments,
Postgres, ingress host, external secrets, container port. It calls
`.claude/scripts/new-app.sh`, which can also be run directly:

```bash
.claude/scripts/new-app.sh --name myapp --host myapp.matejkovac.sk --port 8080 \
  --postgres myapp_db          # or --no-postgres, --no-secrets, --dry-run
  # --env prod --env dev       # default: prod only; dev host defaults to
                               # myapp.dev.matejkovac.sk, or --env dev=<host>
```

It writes these and stops there — no commit, no push, no cluster access:

| File | What it is |
|---|---|
| `environments/<env>/myapp.yaml` | per env: the chart pin (newest `chart-app-*` already in use); the ApplicationSet makes it an Application |
| `applications/myapp/values.yaml` | the app's config |
| `applications/myapp/<env>.yaml` | per env, only when not prod-only: `name`, `host`, database URL |
| `versions/myapp.yaml`, `versions/myapp-<env>.yaml` | `imageTag: change_me` — written by CI from then on |

For a non-prod environment, the steps below are per environment: its own
Infisical folder `/myapp-<env>` (or `secrets.path` /
`secrets.infisical.environmentSlug` in `<env>.yaml` to read another one), its
own database `myapp_db_<env>`, its own DNS name.

### The steps it cannot do

The app will not start until these are done, so do them **before** pushing to
`main` — that push is the deployment.

1. **Infisical folder `/myapp`** — put the app's secrets in it. They arrive as
   env vars via `myapp-secrets`; adding one later needs no commit. Skipped if
   the app was created with `--no-secrets`.
2. **The database**, if the app uses Postgres. Postgres runs in **Docker on the
   VM, not in the cluster** — the chart only renders a selector-less Service
   pointing at the docker0 gateway, so the app can reach it as `postgres:5432`.
   Create the database and a user with rights on it, and put that user and
   password in Infisical `/myapp`:

   ```bash
   createdb -h <vm> -U postgres myapp_db
   ```
3. **DNS** for the host, pointing at the VM. The certificate is issued by an
   HTTP-01 challenge, so the record has to resolve *before* the first sync —
   otherwise the challenge fails and Let's Encrypt rate-limits at 5 failures per
   hour. Use `clusterIssuer: letsencrypt-staging` while testing.
4. **Build and push the image** to `registry.matejkovac.sk/apps/myapp`, then put
   its tag in `versions/myapp.yaml`. `versions/README.md` has the pipeline that
   writes that file on every deploy.
5. **Render it** before pushing, with the value files in the order the
   ApplicationSet uses:

   ```bash
   helm template myapp ../kovostack-helm-charts/charts/app \
     -f applications/myapp/values.yaml -f versions/myapp.yaml
   # an app with environments: add -f applications/myapp/<env>.yaml after
   # values.yaml, and use versions/myapp-<env>.yaml outside prod
   ```

Anything beyond those answers — volumes, init containers, `wwwAlias`,
resources — is a normal edit to `applications/myapp/values.yaml` afterwards.
`charts/app/values.yaml` in the charts repo documents every key and which ones
switch parts of the chart off.

## When the chart does not fit

An app with its own Helm chart can still use the convention for the glue: leave
`image` empty so no workload is rendered, and deploy the workload from a second
Application — which, like every Application now, has to come from somewhere
under git: a second ApplicationSet or a file in `clusters/production/`, not a
manifest in this directory. The namespace, secrets and ingress still come from here.
